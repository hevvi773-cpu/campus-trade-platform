# 第一部分：系统总览

## 1. 产品定位与业务背景

### 1.1 业务背景

校园二手交易平台面向**单一高校（西南大学）在校生**，提供校内二手物品的信息发布、浏览检索、在线沟通与交易撮合能力。平台解决三个具体问题：

1. **信息不对称**：学生二手物品分散在微信群、QQ 空间，无统一检索入口
2. **信任缺失**：买卖双方互不认识，缺乏可查证的信用依据
3. **交易无序**：线下交易无记录、无评价，纠纷无法追溯

平台定位为**信息展示与沟通工具**，明确不参与实际交易过程，不承担交易风险（首页公告已书面声明）。

### 1.2 需求目标

| 目标类型 | Badge | 目标描述 |
|:---------|:------|:---------|
| **业务目标** | `purple` | 商品从发布到上架的审核时长 ≤ 24 小时（超时自动过审兜底） |
| **业务目标** | `purple` | 每个已确认订单产生 1 条有效评价，信用分覆盖 ≥ 60% 活跃用户 |
| **用户体验** | `blue` | 首页首屏渲染 ≤ 2 秒，搜索/标签筛选响应 ≤ 1 秒 |
| **用户体验** | `blue` | 用户从看到商品到发起沟通的路径 ≤ 2 次点击 |
| **安全目标** | `red` | 游客零写权限；被禁言用户零互动权限；全部写接口 CSRF 校验 |
| **安全目标** | `red` | 交易确认码仅卖家可见；登录失败 5 次锁定 10 分钟 |
| **运营目标** | `indigo` | 管理员可在 1 个页面完成审核、禁言、回复反馈三类日常操作 |
| **技术目标** | `slate` | 新增字段走 `ensure_schema()` 自动迁移，生产环境不因缺列 500 |

## 2. 状态机

### 2.1 商品审核状态 `products.status`

| 状态 | Badge | 说明 | 行为影响 |
|------|-------|------|---------|

## 3. 信用体系【已在 v15 移除，本节为 v1~v12 历史记录】

> ⚠️ **V1.4 变更说明**：信用分体系（`credit_score`、`credit_level`、`update_user_credit`）已在 v15 移除。评价体系（1-5 星、发出/收到评价、星级分布图）保留。以下内容为 v1~v12 时期的历史设计，仅供回溯参考。

### 3.1 信用分计算

```
无评价记录：score = 100
有评价记录：
  base_score  = round( 平均星级 × 20 )
  count_bonus = min( 评价条数 × 2, 15 )
  bad_penalty = 1星条数 × 5 + 2星条数 × 2
  score       = max( 0, base_score + count_bonus - bad_penalty )
```

重算时机：每次新评价写入后调用 `update_user_credit(卖家用户名)`。

### 3.2 信用等级

| 等级 | 门槛分 | 文案 | 图标 | 色值 |
|------|-------|------|------|------|
| S | 150 | 信用极好 | 🌟 | #FFD700 |
| A | 120 | 信用优秀 | ✅ | #0d6efd |
| B | 80 | 信用良好 | 👍 | #198754 |
| C | 40 | 信用一般 | ⚠️ | #fd7e14 |
| D | 0 | 信用较差 | ❌ | #dc3545 |

新用户默认 `credit_score=100`、`credit_level='B'`。

> **已知问题**：理论最高分 = 100（全 5 星）+ 15（数量奖励）= **115 分**，因此 S（150）与 A（120）两级**实际不可达**。详见第 9 节 DEV-002。

## 4. 标签体系

| 标签 | 存储方式 | 筛选方式 |
|------|---------|---------|
| 书籍 / 数码 / 生活用品 | `products.tags` 逗号分隔字符串，如 `书籍,数码` | SQL `FIND_IN_SET(%s, p.tags)` |

- 发布时多选，去重后拼接，仅接受白名单内的值
- 标签条件必须位于"可见性 OR 分组"之外，否则卖家自己的商品会绕过筛选（v10 修复项）

## 5. 未读角标口径

角标统一由 `services/notify_service.get_badge_counts()` 计算，三个入口口径不同，**不可混用**：

| 入口 | Badge | 统计口径 | 展示位置 |
|------|-------|---------|---------|
| 消息 | `red` | `messages` 中 `receiver = 我` 且 `is_read = 0` 的条数 | 首页、订单页 |
| 订单 | `red` | `orders` 中 `seller = 我` 且 `status = 'pending'` 的条数 | 首页、消息页 |
| 反馈 | `red` | `feedbacks` 中 `username = 我`、`status='resolved'`、`reply` 非空、`is_read = 0` 的条数 | 首页、订单页、消息页 |

**容错原则**：角标属增强功能，任何查询异常一律退化为 0，绝不允许把页面带成 500。
**首页角标规则**：登录用户在首页导航同样展示消息/订单/反馈三类角标；游客访问首页不展示任何角标。

## 6. 全局交互与安全规范

| 项 | 规范 |
|----|------|
| CSRF | 所有 POST（表单 / fetch）携带 `_csrf_token` 或 `X-CSRF-Token` 请求头 |

### M1.5 核心流程

#### 加载更多

```
用户点击「加载更多」
    ↓
读取按钮 data-page，next = page + 1
    ↓
按钮禁用，文案改为「加载中...」
    ↓
GET /?page=next&ajax=1（保留 q / tag 参数）
    ↓
if 响应 200:
    → 解析统一返回格式（见下方「AJAX 分页统一返回格式」）
    → 三组 items 分别追加到对应 Tab 网格
    → 若该组原有空态占位，先移除
    ↓
if 顶层 has_more = true:
    → 按钮恢复，data-page = next_page
if 顶层 has_more = false:
    → 整个容器替换为「没有更多了」
    ↓
if 响应失败:
    → 按钮恢复，「加载失败，请稍后重试」alert
```

#### AJAX 分页统一返回格式

首页按三个 Tab（出售中 `sell` / 求购中 `buy` / 已售出 `sold`）**独立分页**，每页每组 10 条（`PER_PAGE = 10`），各组各自维护 `has_more`。`ajax=1` 请求统一返回：

```json
{
  "code": 0,
  "data": {
    "sell": { "items": [], "has_more": true },
    "buy":  { "items": [], "has_more": false },
    "sold": { "items": [], "has_more": true },
    "has_more": true,
    "next_page": 2
  }
}
```

- `sell / buy / sold`：对应 Tab 本页追加的卡片 HTML 片段数组（`items`）与该组是否还有下一页（`has_more`）
- 顶层 `has_more`：组合规则为 `sell.has_more ∨ buy.has_more ∨ sold.has_more`，即**任一组仍有下一页即为 `true`**；「加载更多」按钮的显隐只依据顶层 `has_more`
- `next_page`：`当前页码 + 1`，下一次「加载更多」应请求的页码
- 三组追加相互独立：某组 `has_more=false` 后该组不再追加、保持现状，其余组继续随翻页追加

#### 游客交互拦截

```
用户点击 详情/收藏/私信/购买
    ↓
调用 guestGuard(action)
    ↓
if 未登录:
    → alert「请先登录后再{action}」
    → location.href = '/login_page'
    → return true（拦截）
if 处于禁言期:
    → alert「您当前处于禁言期，无法{action}」
    → return true（拦截）
    ↓
return false（放行）
```

## M3 账号、登录与三级权限

### M3.1 需求背景与目标

校园场景要求账号可追溯到真实学生，同时对违规用户具备快速处置能力。系统在"强制实名"与"注册转化"之间做了取舍：学号由必填改为选填。

| 目标类型 | Badge | 目标描述 |
|:---------|:------|:---------|
| 业务目标 | `purple` | 注册转化率因学号选填提升，注册流程 ≤ 30 秒 |
| 安全目标 | `red` | 单「用户名+IP」连续失败 5 次锁定 10 分钟 |
| 安全目标 | `red` | 游客零写权限，禁言用户零互动权限，判定逻辑全站唯一 |
| 运营目标 | `indigo` | 管理员可一键禁言/解禁，单次禁言时长 7 天 |

### M3.2 注册与登录规则

| 项 | 规则 |
|----|------|
| 用户名 | 3~50 字符，仅字母、数字、下划线，全站唯一 |
| 密码 | 非空，注册需二次确认一致 |
| 昵称 | 必填，列表与聊天中展示这个名字 |
| 学号 | **选填**，15 位数字且以 20 开头，全局唯一，可后续补填 |
| 角色 | 注册默认 `student`；`admin` 由系统初始化 |

**登录限流**：同一「用户名小写 + 客户端 IP」连续失败 5 次，锁定 10 分钟；成功登录清空计数。计数存于进程内存，gunicorn 多 worker 不共享，服务重启清零。

### M3.3 页面路由

| 路由 | 说明 |
|------|------|
| `/login_page` | 登录 + 注册同页（注册锚点 `#register`） |
| `/do_login` | 登录 POST |
| `/do_register` | 注册 POST |
| `/logout` | 登出 POST |
| `/fill_student_id` | 补填学号 |

### M3.4 核心流程

```
用户提交登录
    ↓
计算限流 key = 小写用户名 | 客户端IP
    ↓
if 处于锁定期:
    → 返回登录页，提示「失败次数过多，账号已临时锁定，请约 N 分钟后再试」
    ↓
authenticate_user 校验用户名与密码哈希
    ↓
if 校验通过:
    → 清空失败计数
    → 写入 session: username / identity / nickname
    → 写 login_logs（IP、UA）
    → admin → /admin；student → /
    ↓
if 校验失败:
    → 记录一次失败
    → 剩余次数 > 0：「用户名或密码错误（剩余尝试次数：N）」
    → 剩余次数 = 0：「失败次数过多，账号已临时锁定 10 分钟」
```

## M4 订单交易

### M4.1 需求背景与目标

把"聊好了私下去交易"变成有据可查的站内流程，让买卖双方在平台上完成下单、确认、取消，并以订单作为评价的前置条件。

| 目标类型 | Badge | 目标描述 |
|:---------|:------|:---------|
| 业务目标 | `purple` | 已确认订单 100% 可作为评价入口 |
| 用户体验 | `blue` | 从商品卡片到提交订单 ≤ 3 次点击 |
| 安全目标 | `red` | 下单与状态变更使用行级锁，防止超卖与重复下单 |

### M4.2 订单状态与操作

| 状态 | Badge | 说明 | 可执行操作 |
|------|-------|------|-----------|
| 待确认 `pending` | `yellow` | 买家下单，商品锁定 | 卖家：确认交易、取消订单；买家：取消订单 |
| 已确认 `confirmed` | `green` | 卖家确认 | 买家：评价 |
| 已取消 `cancelled` | `gray` | 任一方取消，商品释放 | 无 |

| 操作 | 前置条件 | 生效时间 | 副作用 |
|------|---------|---------|--------|
| 下单 | student 未禁言；商品 approved 且 unsold；非本人商品；本人无该商品 pending/confirmed 订单 | 即时 | 商品置为 sold 并写 sold_time |
| 确认交易 | 当前用户为卖家；订单 pending | 即时 | 订单 confirmed |
| 取消订单 | 当前用户为买家或卖家；订单 pending | 即时 | 订单 cancelled，商品回退 unsold、清空 sold_time |
| 评价 | 当前用户为买家；订单 confirmed；商品未被删 | 即时 | 写入 evaluations 并重算卖家信用分 |

### M4.3 页面路由

| 路由 | 说明 |
|------|------|
| `/orders` | 我的订单列表 |
| `/order/create` | 下单 POST |
| `/order/confirm/<order_id>` | 确认 POST |
| `/order/cancel/<order_id>` | 取消 POST |

### M4.4 页面布局

| 区域 | 内容 |
|------|------|
| 头部 | 「我的订单」标题 + 消息/反馈角标按钮 + 返回首页 |
| 订单卡片 | 商品名、买入/卖出标识、商品已删除徽标、价格、买家、卖家、下单时间、状态徽标、联系方式、留言 |
| 操作区 | 💬 私信买家/卖家；确认交易；取消订单；评价 |

订单按 `created_at DESC` 排序，包含我作为买家与我作为卖家的全部订单。

### M4.5 核心流程

```
买家点击「立即购买」
    ↓
guestGuard 校验登录与禁言
    ↓
打开下单弹窗，填写联系方式与留言（均选填）
    ↓
POST /order/create
    ↓
SELECT ... FROM products WHERE id=? FOR UPDATE
    ↓
if 商品不存在 或 status != 'approved' 或 sold_status != 'unsold':
    → 返回「商品不可购买」
if seller == buyer:
    → 返回「不能购买自己的商品」
if 已存在本人对该商品的 pending/confirmed 订单:
    → 返回「您已对该商品下过订单」
    ↓
INSERT orders（status='pending'）
    ↓
UPDATE products SET sold_status='sold', sold_time=NOW() WHERE id=? AND sold_status='unsold'
    ↓
if 影响行数 != 1:
    → 回滚并返回「商品状态已变化，请刷新后重试」
    ↓
提交事务，写 action_logs，重定向 /orders
```

### M4.6 异常与边界场景

| 场景 | 触发条件 | 系统反馈 | 恢复方式 |
|------|---------|---------|---------|
| 商品已售 | 他人抢先下单 | 「商品状态已变化，请刷新后重试」 | 刷新页面查看最新状态 |
| 重复下单 | 本人已下过单 | 「您已对该商品下过订单」 | 到订单页查看已有订单 |
| 购买自己的商品 | seller == buyer | 「不能购买自己的商品」 | 更换商品 |
| 非卖家点确认 | 买家访问确认接口 | 「只有卖家可以确认订单」403 | 联系卖家确认 |
| 取消已确认订单 | 订单 confirmed | 「订单状态不正确」 | 无法取消，联系对方协商 |
| 商品被删后评价 | 商品记录不存在 | 订单卡片显示「商品已删除」徽标，评价入口不展示 | 无需操作 |
| 禁言用户下单 | 处于禁言期 | 「禁言期间无法下单」403 | 等待解禁 |
| 并发抢单 | 两人同时下单 | 行级锁 + 影响行数校验，后到者失败 | 刷新后重试 |

### M4.7 非功能需求

| 指标 | 要求 | 说明 |
|------|------|------|
| 下单响应 | ≤ 1 秒 | 含行锁等待 |
| 并发安全 | 行级锁 | `SELECT ... FOR UPDATE` |
| 订单查询 | ≤ 1 秒 | 单次 LEFT JOIN 查询 |
| 事务 | 全部或回滚 | 下单、确认、取消均在单事务内 |

### M4.8 验收标准

1. 给定商品为已上架未售出且买家无历史订单，当提交下单，则订单状态为 pending 且商品立即变为已售出
2. 给定买家已有该商品的 pending 订单，当再次提交下单，则返回「您已对该商品下过订单」且不生成新订单
3. 给定订单为 pending，当卖家点击「确认交易」，则订单变为 confirmed 且买家侧出现「评价」按钮
4. 给定订单为 pending，当买家点击「取消订单」，则订单变为 cancelled 且商品回退为未售出可被他人下单
5. 给定订单为 confirmed，当任一方尝试取消，则返回「订单状态不正确」且状态保持不变
6. 给定两个买家同时对同一商品下单，当并发请求完成，则只有一方成功，另一方收到「商品状态已变化，请刷新后重试」
7. 给定用户处于禁言期，当提交下单，则返回「禁言期间无法下单」403

### M4.9 名词字典

| 名词 | 定义说明 | 数据来源 |
|------|---------|---------|
| 视角 | 订单相对当前用户的身份，取值「买入」或「卖出」 | `order_service.perspective` |
| 交易对手 peer | 订单中与我相对的另一方，用于私信跳转 | `routes/orders.py` 计算 |
| 锁定商品 | 下单成功后商品立即置为 sold，防止重复售卖 | `products.sold_status` |

## M5 私信与商品卡片

### M5.1 需求背景与目标

站内私信是交易撮合的主链路。核心诉求是**让双方一进聊天就知道在聊哪件商品**，避免"你问的是哪个"的来回确认。

| 目标类型 | Badge | 目标描述 |
|:---------|:------|:---------|
| 业务目标 | `purple` | 从商品进入的会话 100% 携带商品上下文 |
| 用户体验 | `blue` | 会话列表可直接看出对方身份与来源商品，无需点进聊天 |
| 安全目标 | `red` | 三条越权校验：禁止自聊、对方须存在、无历史且无商品来源禁止访问 |

### M5.2 会话与消息定义

| 实体 | 字段 | 说明 |
|------|------|------|
| 会话 | 对方用户名、对方昵称、最近一条消息、未读数、来源商品 ID、来源商品名、时间 | 按最近消息时间倒序 |
| 消息 | 发送人、内容、时间、product_id（可空） | 按时间正序；进入会话即把对方发来的标记已读 |

### M5.3 页面路由

| 路由 | 说明 |
|------|------|
| `/messages` | 会话列表 |
| `/messages/<receiver>` | 聊天详情，支持 `?product_id=N` |
| `/send_message` | 发送消息 POST（JSON） |

### M5.4 页面布局

**会话列表**

| 区域 | 内容 |
|------|------|
| 头部 | 「💬 我的消息」+ 我的订单/反馈角标 + 返回首页 |
| 会话项 | 对方昵称、**来自商品：{商品名}**、最近消息摘要（截断 30 字）、未读红点、时间 |
| 空态 | 「暂无消息记录」 |

**聊天详情**

| 区域 | 内容 |
|------|------|
| 头部 | 「💬 与 {对方昵称} 的对话」+ 返回列表 |
| 消息区 | 自己的消息右侧蓝气泡；对方消息左侧灰气泡；**带 product_id 的消息渲染为居中粉色商品卡片** |
| 输入区 | 输入框 + 发送按钮 |

**商品卡片规格**：居中排列，宽度 60%（最大 340px，手机端 90%），粉色渐变圆角 22px，左侧 54×54 缩略图（无图显示 📦），右侧商品名（超长省略）+ 已售徽标 + 价格 + 时间，整体可点击跳转 `/?p={product_id}` 新窗口打开。

### M5.5 核心流程

#### 从商品进入会话

```
用户在商品卡片/详情弹窗/收藏页/订单页点击「私信」
    ↓
跳转 /messages/<seller>?product_id=N
    ↓
校验: receiver == 我 → 403「不能和自己聊天」
校验: 对方不存在 → 404「对话用户不存在」
校验: 无历史消息 且 无 product_id → 403「无权访问该对话」
    ↓
_seed_product_card_if_absent:
    ↓
if 会话内已存在相同 product_id 的消息:
    → 不重复插入
if 商品不存在（已删）:
    → 静默跳过
    ↓
INSERT messages（sender=我, receiver=对方, content='我对你的商品「{商品名}」感兴趣，可以聊聊吗？', product_id=N）
    ↓
拉取会话消息并把对方发来的标记已读
    ↓
_enrich_product_messages 批量补全商品价格、图片、是否已售
    ↓
渲染：带 product_id 的消息 → 居中商品卡片；其余 → 左右气泡
```

#### 发送消息

```
用户输入内容并回车
    ↓
POST /send_message（JSON: receiver, content, product_id）
    ↓
校验 student 会话 + 未禁言
校验 receiver 非空且非本人
校验 对方存在
校验 有 product_id 或 双方有历史消息
    ↓
INSERT messages
    ↓
返回 {code: 0, msg: '发送成功'}
    ↓
前端本地追加一条「刚刚」的蓝色气泡并滚动到底部
```

### M5.7 异常与边界场景

| 场景 | 触发条件 | 系统反馈 | 恢复方式 |

3. 给定会话中已有商品 A 的卡片，当用户后续从商品 B 进入同一人的会话，则保留历史聊天记录并在下方新增商品 B 的卡片

# 第五部分：代码实现偏差与遗留问题

> 以下记录当前实现与产品应有逻辑之间的偏差，以及历史遗留问题。

### DEV-001 分享功能已于 v9 整体下线（P1）

**偏差描述**：v5 引入的分享能力（链接复制、QQ/微信分享、聊天内分享，共 13 处引用）在 v9 被全部移除，当前版本不提供任何分享。

| PRD 应有 | 代码实现 | 偏差说明 |
|---------|---------|---------|
| 商品可分享给站外好友 | ❌ v9 起已移除全部分享 JS 与 UI | 原方案依赖 Clipboard API，在非 HTTPS 环境下复制失败且无法长按复制，产品决策改为下线 |

**建议**：如需恢复，优先采用「弹窗展示链接 + 已选中输入框供手动复制」的降级方案，不依赖 Clipboard API。

### DEV-002 信用等级 S 与 A 实际不可达（P2）

**偏差描述**：信用分理论上限为 115（100 + 15），而 S 级门槛 150、A 级门槛 120，两级永远不会出现。

| PRD 定义 | 代码实现 | 偏差说明 |
|---------|---------|---------|
| S ≥ 150 分 | 上限 115 分 | 等级阈值与计算公式不匹配 |
| A ≥ 120 分 | 上限 115 分 | 同上 |

**建议**：将阈值调整为 S≥110、A≥100、B≥80、C≥40、D≥0，或提高数量奖励上限。

### DEV-003 评价为单向，卖家无法评价买家（P2）

**偏差描述**：`evaluate` 路由存在卖家分支，但紧接着被「不能评价自己的商品」拦截，导致卖家永远无法评价买家。

| PRD 应有 | 代码实现 | 偏差说明 |
|---------|---------|---------|
| 买卖双方互评 | 仅买家可评价 | 卖家分支为死代码 |

**建议**：明确产品决策——若坚持单向评价，删除死分支；若改双向，需为卖家提供独立入口并调整 `evaluations` 唯一键（当前为 `product_id` 唯一，双向需改为 `product_id + from_user`）。

### DEV-004 订单未读角标仅覆盖卖家（P2）

**偏差描述**：订单角标统计口径为「我是卖家且 status='pending'」，买家侧的待确认、待评价订单均无角标提醒。

| PRD 应有 | 代码实现 | 偏差说明 |
|---------|---------|---------|
| 买卖双方各有订单角标 | 仅卖家有 | 买家需主动进入订单页才知道状态变化 |

### DEV-005 消息无实时推送（P2）

**偏差描述**：聊天页不发轮询也不使用 WebSocket，对方新消息需手动刷新页面才能看到；发送成功后仅本地追加气泡。

| PRD 应有 | 代码实现 | 偏差说明 |
|---------|---------|---------|
| 新消息实时到达 | 手动刷新 | 影响沟通体验，校园场景可接受但应记录 |

**建议**：短期可加 10 秒轮询，长期考虑 SSE 或 WebSocket。

### DEV-006 登录限流为进程内计数（P2）

**偏差描述**：`_LOGIN_FAILS` 存于进程内存，gunicorn 多 worker 时各自计数（N 个 worker 实际容忍约 N×5 次），服务重启后清零。

| PRD 应有 | 代码实现 | 偏差说明 |
|---------|---------|---------|
| 全局共享限流 | 进程内计数 | 校园规模可接受，规模扩大需换 Redis |

### DEV-007 搜索日志未记录结果数（P3）

**偏差描述**：`log_search(q)` 调用时未传 `result_count`，`search_logs.result_count` 恒为 0。

| PRD 应有 | 代码实现 | 偏差说明 |
|---------|---------|---------|
| 记录每次搜索命中数 | 恒为 0 | 无法基于此字段做搜索质量分析 |

### DEV-008 学号选填后仍保留补填页（P3）

**偏差描述**：v11 将学号改为选填，登录不再强制跳转，但 `/fill_student_id` 路由与模板仍保留。

| PRD 应有 | 代码实现 | 偏差说明 |
|---------|---------|---------|
| 选填即可补填 | 保留但无入口引导 | 入口需在个人中心显式暴露，否则为死页面 |

### DEV-009 未确认订单无超时释放（P2）

**偏差描述**：订单创建后商品即锁定为 sold，若买卖双方都不处理，商品将长期处于锁定状态，无任何超时释放机制。

| PRD 应有 | 代码实现 | 偏差说明 |
|---------|---------|---------|
| 超时未确认自动取消并释放商品 | ❌ 缺失 | 需新增定时任务或懒释放逻辑 |

## A.3 级联删除 / 保留策略

用户注销采用**软删**方案：用户记录保留但禁止登录，关联数据处理如下表；软删与硬删的对比及完整执行流程见附录 C.3。

| 触发动作 | 关联数据 | 处理策略 |
|---------|---------|---------|
| **用户注销** | 用户记录 | **软删**：保留行，清空密码与学号，昵称改为「已注销用户」，禁止登录 |
| | 商品 | 删除商品记录与本地图片文件 |
| | 收藏 | 删除该用户全部收藏记录 |
| | 私信 | 删除消息内容或匿名化处理 |
| | 订单 | **保留**，用于交易追溯 |
| | 评价 | **保留**，from_user / to_user 匿名化 |
| | 反馈 | 删除图片文件，正文可匿名化保留 |
| | 审计日志（action_logs） | **保留**，username 哈希化 |
| | 登录日志（login_logs） | **保留**，按附录 C.2 保留期限到期删除或匿名化 |
| **商品删除** | 订单 | **保留**，订单卡片显示「商品已删除」徽标 |
| | 收藏 | 记录可保留，JOIN 查询后不再展示；建议随商品删除一并清理 |
| | 私信商品卡片 | 消息保留，商品信息缺失时显示 📦 占位 |
| | 评价 | **保留**，信用分不回退 |
| **订单取消** | 商品状态 | `sold_status` 回退 `unsold`，`sold_time` 清空，商品可再次被下单 |
| **反馈删除** | 图片 | 删除磁盘图片文件，避免孤儿文件；正文可匿名化保留 |

> 用户注销的完整流程与隐私合规要求见**附录 C**。

# 附录 B：API 契约

## B.1 通用响应格式

**成功**：

```json
{ "code": 0, "msg": "ok", "data": {} }
```

**失败**：

```json
{ "code": 403, "msg": "无权访问该对话", "data": null }
```

说明：页面型接口（表单 POST）以 302 重定向表达成功；JSON 接口（`/api/product/<pid>`、`/send_message`、`/favorite/toggle/<pid>`、首页 `ajax=1` 分页）统一返回上述响应体。

## B.2 分页格式

通用分页（单列表）：

```json
{
  "code": 0,
  "data": {
    "items": [],
    "page": 1,
    "per_page": 10,
    "total": 25,
    "has_more": true,
    "next_page": 2
  }
}
```

首页三 Tab 分组分页（`GET /?page=N&ajax=1`）见 M1.5「AJAX 分页统一返回格式」。

## B.3 错误码表

| code | 含义 | 典型场景 |
|:----:|------|---------|
| 0 | 成功 | — |
| 400 | 参数错误 | 字段为空、格式不合规、图片格式不支持 |
| 401 | 未登录 | JSON 接口未携带有效会话 |
| 403 | 无权限 / 禁言 / 越权 | 非管理员、禁言期操作、越权访问会话、非卖家确认订单 |
| 404 | 资源不存在 | 商品已删、订单不存在、对话用户不存在、反馈不存在 |
| 409 | 状态冲突 | 重复下单、并发抢单、订单状态不正确、重复评价 |
| 413 | 请求体或文件过大 | 单文件超 5MB 或请求体超 15MB |
| 500 | 服务器错误 | 兜底异常 |

## B.4 CSRF 约定

- 所有 POST 请求**必须**携带 `_csrf_token` 表单字段或 `X-CSRF-Token` 请求头，缺失或校验失败返回 403
- JSON 接口统一使用 `X-CSRF-Token` 请求头
- 表单 POST（下单、收藏、审核、禁言、回复反馈等）使用隐藏域 `_csrf_token`

## B.5 接口明细

### B.5.1 GET /api/product/\<pid\>

**权限**：student / admin；游客与禁言用户 403。

**响应**：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "id": 12,
    "name": "考研数学复习全书",
    "price": "25.00",
    "description": "九成新，无笔记",
    "contact": "微信号 xxx",
    "seller": "stu_001",
    "seller_nickname": "阿橙",
    "seller_rating": 4.5,
    "type": 1,
    "type_text": "出售",
    "tags": "书籍",
    "status": "approved",
    "sold": false,
    "desc_image": "/static/uploads/desc/20260901_120000_000001_book.jpg",
    "contact_image": null,
    "confirm_code": null
  }
}
```

**confirm_code 可见性**：仅当请求者为该商品**卖家本人**时返回 4 位确认码；其余用户（含管理员）恒为 `null`。v12 起收口，此前任何登录用户均可读取。

**错误场景**：403 未登录或禁言；404 商品不存在或已删除。

### B.5.2 POST /send_message

**权限**：student 且未禁言。**请求头**：`X-CSRF-Token`。

**请求体**（JSON）：

```json
{ "receiver": "stu_002", "content": "还在吗？", "product_id": 12 }
```

`product_id` 可选；携带时允许无历史消息直接发起会话。

**响应**：

```json
{ "code": 0, "msg": "发送成功", "data": null }
```

**错误场景**：401 未登录；403 禁言 / 无效的聊天对象 / 无权发起该对话；404 对话用户不存在；400 无效请求 / 接收人和内容不能为空。

### B.5.3 POST /favorite/toggle/\<pid\>

**权限**：登录且未禁言（管理员无收藏能力）。**请求**：POST + `_csrf_token` 或 `X-CSRF-Token`。

**响应**（JSON）：

```json
{ "code": 0, "msg": "ok", "data": { "favorited": true } }
```

`favorited` 为切换后的最终状态：`true` 已收藏，`false` 已取消。前端据此校正爱心状态（乐观更新 + 响应校正）。

**错误场景**：401 未登录（正常流量已被前端 `guestGuard` 拦截，不触达）；403 禁言。

### B.5.4 POST /order/create

**权限**：student 且未禁言。**请求**：表单 `{product_id, contact（选填）, message（选填）}` + `_csrf_token`。

**响应**：302 重定向 `/orders`；订单 `status='pending'`，商品置 `sold` 并写 `sold_time`。

**错误场景**：403 禁言期间无法下单；400 商品不可购买（非上架/已售）/ 不能购买自己的商品；409 您已对该商品下过订单 / 商品状态已变化，请刷新后重试（并发抢单）。

### B.5.5 POST /order/confirm/\<order_id\>

**权限**：订单卖家（student）。**请求**：表单 POST + `_csrf_token`。

**响应**：302 重定向 `/orders`；订单 `confirmed`，买家侧出现评价入口。

**错误场景**：404 订单不存在；403 只有卖家可以确认订单；409 订单状态不正确（非 pending）。

### B.5.6 POST /order/cancel/\<order_id\>

**权限**：买家或卖家。**请求**：表单 POST + `_csrf_token`。

**响应**：302 重定向 `/orders`；订单 `cancelled`，商品回退 `unsold`、清空 `sold_time`。

**错误场景**：404 订单不存在；403 无权限；409 订单状态不正确（已取消或已确认）。

### B.5.7 POST /feedback/submit

**权限**：student。**请求**：表单 `{title（必填）, content（必填）, image（选填，最多 1 个文件）}` + `_csrf_token`。

**响应**：302 重定向 `/feedback`；反馈 `status='pending'`。写入失败时已落盘图片自动删除，不产生孤儿文件。

**错误场景**：400 标题和内容不能为空 / 图片格式不支持；413 文件过大，请压缩后重试（单文件超 5MB 或请求体超 15MB）。

### B.5.8 POST /admin/reply_feedback/\<fid\>

**权限**：admin。**请求**：表单 `{reply（必填）}` + `_csrf_token`。

**响应**：302 重定向 `/admin`；反馈 `status='resolved'`，用户侧产生未读角标。

**错误场景**：403 无管理员权限；400 回复内容不能为空；404 反馈不存在。

## B.6 与当前实现的差异说明

本契约为**目标口径**：未登录统一 401、状态冲突统一 409。v12 实现中 `/send_message` 未登录返回 403、下单与订单类冲突部分返回 400，后续版本按本契约对齐，对齐前以实际返回为准。

## C.2 IP / UA 与日志保留期限

| 日志字段 | 保留期限 | 到期处理 |
|---------|---------|---------|

## C.3 用户注销统一流程

管理员执行 `/delete_user/<username>` 后，按以下顺序处理（目标流程，完整级联策略见附录 A.3）。

**硬删 / 软删方案对比**：

| 方案 | 用户记录 | 关联数据 | 结论 |
|------|---------|---------|------|
| 硬删 | 物理删除 `users` 行 | 订单、评价、审计日志失去关联主体，交易追溯断裂 | 不推荐 |
| **软删（采用）** | 保留行：清空密码与学号、昵称改「已注销用户」、禁止登录 | 订单与评价可追溯，审计日志可哈希保留，逻辑外键完整 | **推荐并采用** |

**软删统一流程**：

1. **用户记录**：清空密码与学号，昵称改为「已注销用户」，禁止登录
2. **商品**：删除商品记录与本地图片文件
3. **收藏**：删除该用户全部收藏记录
4. **私信**：删除消息内容或匿名化处理
5. **订单**：保留，用于交易追溯
6. **评价**：保留，from_user / to_user 匿名化
7. **反馈**：删除图片文件，正文可匿名化保留
8. **审计日志**：保留，username 哈希化
9. **旧 session**：被注销用户访问 `/profile` 时清 session 并跳转登录页（v12 已实现）

> **现状说明**：当前实现为硬删变体——删除商品与图片后直接删除 `users` 记录，未执行软删与其余级联步骤，已登记为 **DEV-013**，落地时按本节流程对齐。
